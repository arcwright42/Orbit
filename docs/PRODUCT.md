# Orbit 产品需求

版本：0.1 草案  
更新日期：2026-10-09  
状态：产品定位与核心职责已确认；首版取舍和验收细则为拟定方案。

Orbit 是面向个人用户的桌面 AI 工作空间。用户通过一个常驻交互 Agent，用文本、语音和多媒体附件表达目标；交互 Agent 调用平台工具组织执行团队、派发任务、跟进进度和呈现结果。具体工作由执行团队完成。

Orbit 的团队协作能力以 OpenRig 为主要参考，同时融合 Relay 的桌面入口、持续对话和个人资料体验。产品应让用户无需掌握终端命令、团队配置文件和运行时术语，也能使用持续工作的 Agent 团队。

## 1 已确认的产品方向

以下内容作为当前需求基线。

- 提供客户端，交互面向个人用户，降低 OpenRig 的使用门槛。
- 大部分团队协作功能可以与 OpenRig 相近，包含团队编排、任务派发与持续协作。
- 提供一个常驻交互 Agent，作为用户统一主入口。
- 主入口支持文本输入、语音交互和多媒体文件传输。
- 常驻交互 Agent 具有平台工具调用能力，可以自动组织团队并派发任务。
- 常驻交互 Agent 不承担具体执行工作。
- 执行团队工作时，用户仍可以与常驻交互 Agent 对话、追问进度或提出其他需求。
- 融合本机 Relay 项目的已有能力；具体代码复用方案另行确定。
- 首版使用 TypeScript 快速开发。Relay 的产品能力与交互经验作为参考，不要求沿用其 Rust 和 GPUI 技术栈。
- 实现过程中持续阅读 OpenRig 源码，团队编排与任务协作初版尽可能对齐其实现，跑通基础版本后再逐步改进和创新。
- 架构不追求绝对优雅，但必须明确领域职责与状态归属，便于后续独立优化和迭代。

下文是为实现上述方向拟定的产品规则。平台覆盖、模型供应、首版媒体格式和上线指标尚未定案，见第 12 节。

## 2 用户与使用目标

初期面向希望通过 AI 持续完成工作、但不希望手动管理多个 Agent 会话的个人用户。场景可以包含软件开发、资料研究和内容制作；首发主场景尚待选择。

用户希望直接表达目标、补充资料和判断结果。平台负责把这些输入转化为可追踪的任务，并让用户随时知道进展和需要自己处理的事项。

典型场景：

| 场景 | 用户输入 | 预期体验 |
| --- | --- | --- |
| 开始工作 | “参考这份文档，帮我做一个网站” | 主入口接收文档，澄清关键约束，组织团队并返回任务卡 |
| 持续交流 | 网站制作中，用户提出另一项研究需求 | 原任务继续运行，新需求独立派发，主对话保持可用 |
| 补充要求 | “网站改成深色风格” | 识别对应任务，记录需求变更并转达团队，展示是否已接收 |
| 查询进度 | “刚才那个任务怎么样了” | 根据实际任务状态汇报进度、阻塞和下一步 |
| 处理决定 | 执行团队需要用户选择方案或授权 | 主入口呈现上下文和选项，用户回复后恢复对应任务 |
| 验收成果 | 团队提交文件、代码或预览 | 用户查看成果，选择接受或提出修改，后续工作沿原任务继续 |

## 3 产品角色与职责

### 常驻交互 Agent

它是用户长期交流的对象，负责需求理解、必要澄清、任务关联、平台调度和信息汇总。

允许承担的工作：

- 理解文本、语音转写和平台提供的附件摘要或元信息。
- 识别新任务、已有任务追问、需求变更和普通交流。
- 创建或复用团队，选择团队模板和可用执行 Agent。
- 创建任务，附上目标、资料、约束和验收要求。
- 查询任务状态，转达用户反馈，处理暂停、继续和取消请求。
- 汇总团队已经提供的进展与结果，向用户提出必要问题。

不承担的工作：

- 不直接编程、执行命令、开展研究、编辑用户文件或制作交付物。
- 不自行代替执行 Agent 完成任务，也不绕过团队验收步骤。
- 不因团队失败而临时扩大自身执行权限。

涉及实质工作的请求，即使工作量很小，也交给执行 Agent。问候、需求澄清、平台帮助和已有结果的解释可以直接回答。复杂附件分析属于执行工作；主入口可以接收文件并交由具备能力的 Agent 处理。

### 团队负责人

接收交互 Agent 派发的目标，负责团队内部的任务拆解、人员协调、交接和结果整合。团队规模较小时，可由一个执行 Agent 同时承担负责人职责。

### 执行与检查 Agent

执行 Agent 完成具体工作并提交成果；检查 Agent 按任务要求检查成果和提供反馈。是否需要独立检查由任务类型、模板和用户要求决定，避免每个简单任务都启动完整团队。

### 平台

平台持有团队、任务、会话、附件、授权和执行记录，并落实权限及状态转换。Agent 的文字表述不能替代平台实际状态。

## 4 主入口与交互

### 持续主对话

- 默认进入同一个持续主对话，话题变化不会自动切换到执行线程。
- 每个派发任务在主对话中生成可打开的任务卡，显示名称、状态、负责团队和最近进展。
- 可以从主对话打开任务详情，查看团队内部进度与成果；返回后继续主对话。
- 用户提到“这个”“刚才那个”等对象且存在歧义时，使用简短选择明确目标。
- 长任务派发后释放主入口，不等待执行结束才允许用户继续输入。
- 多项任务的更新必须标明所属任务，不能混入其他任务的对话或资料。

“常驻”表示入口持续可用、身份和历史连续，不表示模型始终推理或持续消耗额度。主对话不依赖无限增长的单个模型上下文。

### 文本与语音

- Qwen 实时模型原则上只用于语音交互。用户直接输入文字时，走独立的文本模型，不默认调用语音模型。
- 文本模型支持本地设置协议、服务地址、模型名称和密钥；不要求用户修改代码或语音配置。
- 文本交互使用 Pi harness 的原生 Session/Compaction，仅提供平台调度工具；不把常驻入口变成具体任务执行者。文本工作窗口设为 256K，语音使用较短历史；压缩只改变模型工作上下文，不删除原始 History。
- 文本与语音共享产品身份、平台工具和持久 History，底层模型会话及配置分别管理。Qwen 用户转写和助手回复必须入 History；先语音后文本能够继续原需求，反向切换也保持连续，不能因切换或重启丢失对话记录。

- 支持多行输入、发送、取消当前回复，以及在任务执行中追加要求。
- 支持语音输入和语音回复，录音、识别、等待和播放状态清晰可见。
- 用户可以中止录音、打断播报，并在语音和文字之间切换。
- 识别失败时保留可恢复输入并支持重试或改用文字；不能把空转写当成任务发出。
- 首版建议优先提供按键录音；唤醒词和连续语音作为后续增强，复用 Relay 的相关经验。
- 停止播报、取消交互 Agent 当前回复、取消后台任务是不同操作，界面必须区分。

### 多媒体附件

- 主入口支持添加文件，展示名称、类型、大小和处理状态，并允许发送前移除。
- 目标范围涵盖图片、文档、音频和视频。具体格式、大小及处理能力按阶段开放。
- 附件与消息及任务绑定，执行团队能够获取本次任务明确提供的资料。
- 发送前提示不支持的格式、超限文件和不可访问文件；禁止静默丢弃附件。
- 区分“文件已接收”和“内容已解析”，不能用上传成功暗示 Agent 已理解内容。
- 当执行 Agent 无法直接处理某类媒体时，由平台处理服务或专门执行 Agent 转换，并记录来源和失败状态。
- 成果支持文件下载或本地打开；适用格式提供预览。传输至远端模型前应清楚呈现资料使用范围。

## 5 自动团队编排与平台工具

用户可以通过自然语言完成编排，图形管理页作为查看和手动调整入口。

| 平台能力 | 交互 Agent 可执行的操作 | 产品约束 |
| --- | --- | --- |
| 能力发现 | 查询可用 Agent、连接状态和团队模板 | 不选用不可用或不支持任务输入的执行者 |
| 团队管理 | 创建、复用、启动和调整团队 | 默认选择足够完成任务的最小团队 |
| 任务派发 | 创建任务、指定团队、绑定资料和验收要求 | 成功后返回持久任务标识和实际状态 |
| 状态查询 | 读取进度、阻塞、执行反馈和成果 | 无法查询时明确显示未知或离线 |
| 需求变更 | 补充输入、转达反馈、调整任务要求 | 保留变更记录及团队接收状态 |
| 执行控制 | 请求暂停、继续、取消和重试 | 以执行层确认结果为准 |
| 人工决策 | 呈现问题、记录用户决定并转交执行方 | 决定必须关联具体任务与请求 |

以上是产品能力定义，不预设最终工具名称或接口协议。

普通编排与派发在用户已授权范围内自动进行；缺少关键目标、出现冲突或需要新的操作权限时再提问。重复请求或网络重试不得重复创建同一任务或重复触发操作。

平台工具只向常驻交互 Agent 提供编排所需能力。执行端的通用终端、文件修改等工具不应默认暴露给它。

## 6 团队与任务管理

Orbit 的团队能力目标包含角色配置、多 Agent 协作、多种运行时接入、任务交接、共享资料、状态持久化和恢复。首版以选定场景所需的核心能力为交付范围，不承诺逐项复制 OpenRig 的所有功能。

任务至少记录：目标、来源消息、用户约束、验收要求、关联附件、负责团队、当前状态、进展、阻塞、成果及历史。

建议用户可见状态：

| 状态 | 含义 |
| --- | --- |
| 待开始 | 已创建，正在等待执行资源或前置条件 |
| 进行中 | 执行方已接收并开始工作 |
| 等你处理 | 有明确的问题、决定或授权等待用户 |
| 已暂停 | 执行层已确认暂停，等待继续 |
| 遇到问题 | 当前无法继续，需要修复、重试或更换执行者 |
| 待验收 | 已有成果，等待验收 |
| 已完成 | 已满足本任务的验收规则 |
| 已取消 | 已确认停止后续执行，保留此前记录和成果 |

暂停和取消未确认前展示“正在暂停”或“正在取消”。对于不支持暂停的运行时，应解释可用替代操作。取消不会自动撤销已经发生的文件变更或外部操作。

任务完成不能仅由 Agent 说“完成了”触发。任务应绑定成果与验收依据；需要用户验收的工作先进入待验收。无文件型成果可以是有依据的结论或操作回执。

## 7 上下文与持续性

- 主对话、任务线程和执行会话分别管理，保持明确的关联关系。
- 常驻交互 Agent 读取跨任务概况；执行团队默认只取得本任务需要的上下文。
- 附件、要求与验收标准归平台任务所有，不依赖某个 Agent 会话独占保存。
- 用户补充要求形成可追溯版本，避免正在执行的轮次被无记录地改变输入。
- 客户端重启后恢复主对话、任务列表、待处理问题和已有成果。
- 执行会话恢复失败时明确说明，提供重试或重新启动路径，不把新会话呈现为完整恢复。
- 关闭窗口后常驻属于首版建议；退出应用、电脑休眠后团队是否继续运行，取决于执行部署方案，必须明确呈现。
- 长期个人记忆作为后续增强，可参考 Relay 的 Memory Provider；用户应能查看、关闭和删除相应记忆。

## 8 界面结构

| 页面或区域 | 主要内容 |
| --- | --- |
| 主入口 | 持续对话、文本与语音输入、附件、任务卡、需要用户处理的问题 |
| 任务 | 活跃与历史任务、状态筛选、任务详情、需求变更、执行控制和成果 |
| 团队 | 可用模板、运行团队、成员角色、状态及手动调整 |
| 文件 | 已提供资料与任务成果，支持关联任务、预览和本地打开 |
| 设置 | Agent 连接、语音、通知、权限、数据和后续用量设置 |

首页优先呈现用户目标、进展和成果。终端、拓扑、原始日志和运行时细节放入可展开的高级视图。

通知优先覆盖“需要用户处理”“成果可验收”和“执行失败”。高频内部交接聚合为进展，避免每个 Agent 动作都打断用户。

## 9 权限与异常体验

- 平台编排权限与具体执行权限分开管理，创建团队不等于授权任意外部操作。
- 执行方需要新权限时，主入口展示对象、操作和影响，并将用户决定回传到原请求。
- 启动失败、连接断开、认证失效、额度不足和资料处理失败均有可读原因与下一步入口。
- 不展示无依据的进度百分比、完成时间或费用数字。运行时不提供相应信息时明确标为不可用。
- 用户消息与平台指令分开处理，附件内容不能自行扩大平台工具权限。
- 重试保留原始输入和已有成果，并避免重复执行已确认完成的操作。

## 10 首版建议与后续范围

### 首版完整流程

首版建议以 macOS 为起点，完成“主入口提出目标 → 自动组织团队 → 执行 → 反馈 → 验收”的完整流程。

| 优先级 | 范围 |
| --- | --- |
| P0 | 常驻主入口、持续文本对话、按键语音输入与语音回复 |
| P0 | 附件添加、基础图片和文档支持、任务资料传递、成果打开 |
| P0 | 平台工具驱动的团队创建或复用、任务派发、状态查询与用户反馈 |
| P0 | 至少一种真实 Agent 运行时，支持最小团队与多任务隔离 |
| P0 | 任务详情、待处理问题、取消、失败处理、持久化和恢复 |
| P0 | 可验证成果与验收流程，主入口和执行职责隔离 |
| P1 | 多种运行时混合团队、更多团队模板、手动角色调整 |
| P1 | 更多媒体格式、音视频内容处理、更完整的成果预览 |
| P1 | 全局快捷入口、语音唤醒、个人记忆与更完整的暂停恢复 |
| 后续 | 跨机器执行、跨设备同步、团队模板市场及更多 OpenRig 高级能力 |

此表是首版取舍建议，不代表将完整产品范围限制为 P0。首版不以大规模 Agent 数量或完整拓扑编辑器为验收目标。

## 11 首版验收场景

| 编号 | 操作与条件 | 通过标准 |
| --- | --- | --- |
| A01 | 用户用文字提交一个需要具体执行的目标 | 交互 Agent 调用平台工具生成任务并交给执行方，自身不调用具体执行工具 |
| A02 | 用户用语音提出同类需求 | 可见转写与任务归属，能够中断播报，并继续用文字追问 |
| A03 | 用户附带图片或支持的文档 | 附件出现在任务资料中，执行方能够获取；解析失败明确显示 |
| A04 | 任务执行中提交第二项独立需求 | 主入口可用，两项任务分别记录、派发与展示状态 |
| A05 | 团队已运行但进展查询失败 | 不编造进度，展示查询异常，既有任务不重复创建 |
| A06 | 用户对指定任务追加要求 | 留下变更记录，并展示执行方是否已接收；其他任务不受影响 |
| A07 | 执行方请求用户决定 | 主入口呈现关联任务和问题，回复传递给正确请求 |
| A08 | 用户取消任务 | 显示请求中与最终结果的区别，历史成果保留，主对话继续可用 |
| A09 | 客户端重启或执行会话丢失 | 恢复持久记录，准确区分恢复成功、待恢复和失败 |
| A10 | 团队提交成果 | 用户能打开结果并验收或要求修改，任务状态与验收结果一致 |
| A11 | 任务派发响应丢失并重试 | 同一派发不会生成重复任务或启动重复团队 |
| A12 | 执行方不可用 | 提示连接或认证问题及恢复入口，交互 Agent 不越权代做 |

衡量产品效果时，优先观察首次成功交付率、从输入到成功派发的耗时、无人工修复的执行比例、主入口可用性、用户验收率和每项任务的交互次数。具体目标值在选定场景和完成原型验证后确定。

## 12 开发路线与架构约束

### 首版开发路线

使用 TypeScript 快速构建可用版本。团队编排、任务归属、交接、运行时管理与恢复等能力，按实际开发顺序对照 OpenRig 源码，优先采用已有实现思路和行为规则。

每实现一项编排能力，先明确对应的 OpenRig 模块及参考版本，再决定直接复用、适配或按相同行为实现。记录必要差异，便于后续排障和跟进上游。对齐重点是可运行的行为与状态规则，不要求把上游全部功能和目录结构搬入 Orbit。

### 领域边界

以下边界是首版代码组织与状态归属的约束，不要求对应独立服务、进程或发布包。

| 领域 | 负责内容 | 边界 |
| --- | --- | --- |
| 交互与会话 | 主对话、用户意图、澄清、平台工具调用与汇报 | 通过平台用例调度工作，不直接执行任务或改写任务状态 |
| 团队编排 | 团队模板、成员角色、团队生命周期和任务路由 | 管理团队关系，不承担具体运行时协议实现 |
| 任务协作 | 任务归属、交接、依赖、状态、人工决策与验收 | 作为任务状态的唯一写入入口，不由 UI 或交互 Agent 各自维护副本 |
| Agent 运行时 | 连接、认证、会话启动、消息传递、取消与恢复 | 将执行事件交给任务领域处理，不自行判定产品任务已验收 |
| 资料与成果 | 附件、上下文引用、文件和交付物 | 明确资料归属与访问范围，不嵌入团队调度逻辑 |
| 客户端交互 | 页面、语音入口、通知、快捷入口和状态展示 | 调用应用接口，不直接操作领域存储或承载编排规则 |

领域之间通过明确的函数、接口或事件协作。数据库、文件系统和外部服务作为实现依赖接入；同一业务状态只有一个负责修改的领域。跨领域流程可以由薄的应用层协调。

### 控制架构复杂度

- 优先单体模块化，允许同一进程和数据库承载多个领域。
- 按真实用例建立必要边界，不预先构造通用工作流引擎、插件框架或复杂微服务体系。
- 允许局部实现朴素，但不把 UI、模型调用、任务状态与进程管理集中在一个模块中。
- 首版不要求支持所有供应商；运行时差异集中在适配边界，避免散落到产品流程。
- 验证重点放在任务派发、交接、恢复和职责隔离等实际行为上。
- 后续优化能够在领域内部开展；变更接口或持久状态时，明确兼容和迁移方式。
